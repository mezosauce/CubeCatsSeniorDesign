## Purpose and Scope
### Purpose
In collaboration with the University of Cincinnati CubeCats organization, this Requirements Document establishes the functional, non-functional, interface, and regulatory baseline for the initial prototype flight software of the On-Board Computer (OBC) on the HABSat-1 3U CubeSat mission. HABSat-1 is designed to capture multispectral imagery (620 nm, 650 nm, 680 nm, and 708 nm wavelengths with a 10 nm FWHM bandwidth) and truth imagery of Harmful Algal Blooms (HABs) in Lake Erie from Low Earth Orbit (LEO) at a Ground Sampling Distance (GSD) below 90 meters per pixel (`L0-PRJ-001`, `L1-SCI-008`, `L1-SCI-009`). This document governs flight software implementation, software-in-the-loop (SITL) and hardware-in-the-loop (HITL) verification, and Preliminary Design Review (PDR) evaluation.
### Scope
The HABSat-1 OBC flight software executes on the primary Main Computer (EnduroSat OBC Type I board with an STM32F407VG ARM Cortex-M4 microcontroller running FreeRTOS and the NASA F' framework) and coordinates with the dedicated secondary Data Processor (RP2350 coprocessor). Within scope for the OBC flight software are:
- **Command and Data Handling (CDH):** Receiving, decrypting (`L3-OBC-129`, `L4-OBC-185`), authenticating (`L3-OBC-130`, `L4-OBC-186`–`189`), validating (`L3-OBC-131`, `L4-OBC-190`–`193`), queuing (`L3-OBC-168`, `L4-OBC-197`–`198`), and dispatching uplinked telecommands from the Ground Station, and returning positive/negative acknowledgments (`L3-OBC-132`, `L4-OBC-194`–`196`).
- **Autonomous Mission & Pass Sequencing:** Managing the deterministic 10-mode Finite State Machine across Pre-Launch, Initialization, Checkout, Standby, Imaging, Downlink, Repeater, Low-Power, Safe, and Emergency modes (`L3-OBC-137`, `L4-OBC-209`–`211`) and executing the event-driven orbital imaging pass sequencer (`L3-OBC-151`–`154`, `L4-OBC-234`–`243`).
- **Subsystem Orchestration & Health Monitoring:** Polling telemetry from all onboard subsystems every 60 seconds (`L3-OBC-138`, `L4-OBC-220`–`221`, `L4-OBC-231`–`233`) and handling asynchronous fault alerts within 100 ms (`L3-OBC-139`, `L4-OBC-222`) across the ADCS, Power Computer (EPS), Imager Adapter, Data Processor, Data Storage, UHF Telemetry/Command Radio, S-Band Main Downlink Radio, Secondary Payload, and Deployment Mechanisms.
- **On-Board Science Processing & Storage Management:** Commanding Cyanobacteria Index (CI) calculation on the Data Processor (`L3-OBC-167`, `L4-OBC-244`–`246`), tagging images with synchronized ECEF position and LVLH attitude metadata (`L3-OBC-173`, `L4-OBC-260`), performing lossless compression and CRC verification (`L3-OBC-146`, `L4-OBC-223`–`224`), and retaining captured images in non-volatile memory until an explicit Ground Station purge command is received (`L3-OBC-147`, `L4-OBC-225`).
- **Fault Detection, Isolation, and Recovery (FDIR):** Managing hardware watchdog timers (`L4-OBC-250`, `L4-OBC-258`), internal bus fault recovery and node isolation (`L3-OBC-160`, `L4-OBC-252`, `L4-OBC-263`), golden-image boot recovery (`L3-OBC-166`, `L4-OBC-251`), and autonomous Safe Mode transitions (`L3-OBC-161`–`162`, `L4-OBC-254`–`255`).

### User Stories (Week 4 Baseline)
- **US-01 (Primary — Satellite Operator):** As a satellite operator, I want to send authorized commands to HABSat-1 and receive confirmation that the commands were processed, so that I can control spacecraft operations and verify that the satellite received my instructions.
- **US-02 (Secondary — Environmental Data Researcher):** As an environmental data researcher, I want HABSat-1 to collect multispectral images with their corresponding observation time and mission data, so that I can use the collected data to analyze harmful algae blooms in the Great Lakes.
- **US-03 (Secondary — Future Club Members):** As a future CubeCats member working on the next satellite mission, I want to be able to learn from the HABSat-1 flight software documentation and development decisions, so that I can understand how the previous mission was designed and use that knowledge when developing the next satellite.
- **US-04 (Hidden — Amateur Radio Operator):** As a licensed amateur radio operator communicating with HABSat-1, I want to understand and follow the satellite's communication requirements and procedures, so that I can communicate with the satellite in accordance with the mission's operating procedures and applicable amateur radio regulations.
### Core Use Case & Acceptance Criteria (`UC-01`: Send and Process Spacecraft Command)
- **Story:** `US-01` | **Primary Actor:** Satellite Operator | **Secondary Actors:** Ground Station, HABSat-1 On-Board Computer (OBC), Satellite Subsystem
- **Preconditions:**
  1. HABSat-1's OBC is powered on and the flight software is running.
  2. The ground station has an established communication link with HABSat-1.
  3. The satellite operator is authorized to send commands to HABSat-1.
  4. The command is supported by the flight software.
  5. The command is valid for the satellite's current mission flight state.
- **Main Success Flow:**
  1. **Satellite Operator:** Selects an authorized command to send to HABSat-1.
  2. **Ground Station:** Formats and transmits the command to HABSat-1 using the established communication protocol.
  3. **OBC:** Receives the command from the ground station.
  4. **OBC:** Validates the command's format, authorization, and compatibility with the current mission flight state.
  5. **OBC:** Routes the validated command to the appropriate satellite subsystem.
  6. **Satellite Subsystem:** Receives and executes the command.
  7. **Satellite Subsystem:** Returns the execution status to the OBC.
  8. **OBC:** Records the command and its execution status.
  9. **OBC:** Transmits a command confirmation to the ground station.
  10. **Ground Station:** Receives the confirmation and makes the command status available to the satellite operator.
  11. **Satellite Operator:** Verifies that the command was successfully processed.
- **Alternate Flow (`A1: Command is scheduled for later execution`):**
  1. **Satellite Operator:** Sends a valid command with a specified future execution time.
  2. **OBC:** Validates the command and verifies that the scheduled execution time is valid.
  3. **OBC:** Stores the command in the scheduled task queue.
  4. **OBC:** Sends confirmation to the ground station that the command has been accepted for scheduled execution.
  5. **OBC:** Waits until the scheduled execution time.
  6. **OBC:** Executes the command and sends the execution status to the ground station.
- **Exception Flow (`E1: Invalid or unauthorized command`):**
  1. **Satellite Operator:** Sends a command to HABSat-1.
  2. **OBC:** Receives the command and determines that the command is malformed, unauthorized, unsupported, or invalid for the current mission flight state.
  3. **OBC:** Rejects the command without sending it to the affected subsystem.
  4. **OBC:** Sends a command-rejection status to the ground station.
  5. **Ground Station:** Presents the rejection status to the satellite operator.
- **Postconditions:** If the command is valid and successfully executed, the requested spacecraft operation has been performed and the command's execution status has been recorded and reported to the ground station. If the command is rejected, the requested operation has not been performed and the rejection and reason have been reported to the ground station.
- **Acceptance Criteria:**
  - **AC-01.1 (Successful Command):** Given the OBC is running, the ground station has an established communication link, and the satellite operator is authorized to send a command that is valid for the current mission flight state, when the satellite operator sends the command to HABSat-1, then the OBC shall validate the command, route it to the appropriate subsystem, and provide the ground station with the command's execution status.
  - **AC-01.2 (Scheduled Command):** Given the OBC is running and receives a valid command with a valid future execution time, when the scheduled execution time is reached, then the OBC shall execute the command and record the resulting execution status.
  - **AC-01.3 (Invalid Command):** Given the OBC receives a command that is malformed, unauthorized, unsupported, or invalid for the current mission flight state, when the OBC validates the command, then the OBC shall reject the command, shall not send it to the affected subsystem, and shall record the reason for rejection.
## Glossary of Domain Terms and Role Names
| Term / Role Name | Definition |
| :--- | :--- |
| **ADCS (Attitude Determination and Control System)** | The spacecraft subsystem (attitude sensors, reaction wheels, magnetorquers, GPS receiver, and ADCS Computer) responsible for determining orbital position/orientation and pointing the satellite. |
| **Amateur Radio Operator** | A hidden external stakeholder holding an amateur radio license who receives public UHF telemetry beacons and relays packets through the HABSat-1 digipeater (`US-04`). |
| **ASCON-AEAD128** | The NIST-standardized lightweight Authenticated Encryption with Associated Data (AEAD) cipher (128-bit key, 16-byte IV, 16-byte authentication tag) used to encrypt and authenticate non-amateur HABSat-1 telecommands and private telemetry. |
| **CAN Bus (Controller Area Network)** | A noise-immune, differential multi-drop serial bus (CAN 2.0B) using fixed 12-byte frames for deterministic command and telemetry exchange between the Main Computer, ADCS, Power Computer, Imager Adapter, and Data Processor. |
| **CDH (Command and Data Handling)** | The core flight software discipline responsible for telecommand ingestion, validation, task scheduling, health monitoring, and telemetry/payload data routing. |
| **CI (Cyanobacteria Index)** | The NOAA-derived optical band-ratio algorithm applied to 620 nm, 650 nm, 680 nm, and 708 nm multispectral bands to quantify harmful algal bloom concentration (`L1-SCI-008`, `L4-OBC-244`). |
| **CRC (Cyclic Redundancy Check)** | An error-detecting code appended to communication frames and stored files to detect bit-flip corruption across noisy RF links, serial buses, or flash memory (`L4-OBC-224`). |
| **CubeCats** | The University of Cincinnati student spacecraft engineering organization developing the HABSat-1 mission. |
| **CubeSat (3U)** | A nanosatellite conforming to the CubeSat Design Specification with a 3-unit form factor (`L2-SYS-026`) and a maximum mass of 6,000 grams (`L2-SYS-027`). |
| **Data Processor (DP)** | The dedicated secondary coprocessor (RP2350) that ingests raw frames from the Imager Adapter over UART, computes the Cyanobacteria Index (`L3-OBC-167`), performs lossless compression, and streams imagery to the S-Band radio. |
| **Data Storage (DS)** | The onboard non-volatile memory subsystem comprising radiation-tolerant SPI MRAM (for critical state flags and timers, `L3-OBC-145`) and SPI NAND Flash (for telemetry logs and captured images, `L3-OBC-144`). |
| **Digipeater** | A digital amateur radio repeater mode in which the UHF transceiver receives, buffers (`L4-OBC-207`), and rebroadcasts unencrypted amateur radio packets (`L2-MIS-080`, `L3-OBC-155`). |
| **DMA (Direct Memory Access)** | Hardware controller capability allowing peripherals (UART, SPI, CAN) to transfer data directly to/from SRAM without saturating the CPU core. |
| **ECEF (Earth-Centered, Earth-Fixed)** | A Cartesian spatial reference frame rotating with the Earth, used to tag the geographical position of the spacecraft during image capture (`L2-SYS-041`, `L3-OBC-173`). |
| **EnduroSat OBC Type I** | The space-qualified PC/104 On-Board Computer hardware platform hosting the primary STM32F407VG ARM Cortex-M4 processor and auxiliary inertial/magnetic sensors. |
| **Environmental Data Researcher** | A secondary stakeholder who uses HABSat-1's downlinked multispectral imagery and CI maps to monitor and model harmful algal blooms (`US-02`). |
| **EPS / Power Computer** | The Electrical Power Subsystem controller that regulates solar array MPPT charging, monitors battery State of Charge (SoC), switches subsystem power rails (`L4-OBC-210`), and monitors the OBC heartbeat (`L4-OBC-258`). |
| **F' (NASA F Prime)** | An open-source (Apache 2.0), component-driven flight software framework developed by NASA JPL featuring static memory allocation and strongly typed message-passing ports. |
| **Faculty Advisor** | Dr. Will Hawkins III, UC Computer Science faculty member providing technical oversight, architecture review, and tie-breaking governance for the OBC Senior Design team. |
| **FreeRTOS** | An open-source (MIT) preemptive real-time operating system kernel providing deterministic priority-based task scheduling (`L4-OBC-247`) and mutex/queue primitives on the ARM Cortex-M4. |
| **Future Club Members** | Secondary stakeholders consisting of incoming UC CubeCats students who will maintain, test, and adapt the HABSat-1 codebase for subsequent missions (`US-03`). |
| **FWHM (Full Width at Half Maximum)** | The spectral bandwidth (10 nm for HABSat-1, `L1-SCI-008`) across which an optical bandpass filter transmits at least 50% of peak intensity. |
| **GPIO (General-Purpose Input/Output)** | Discrete digital hardware pins controlled by the Main Computer to trigger burn-wire deployment mechanisms and read microswitch feedback (`L4-OBC-214`, `L4-OBC-215`). |
| **Ground Station (GS)** | The University of Cincinnati earth terminal (UHF and S-Band antennas, transceivers, F' GDS, SQLite database, and React dashboard) used to command and monitor HABSat-1. |
| **GSD (Ground Sampling Distance)** | The physical distance on the Earth's surface represented by a single image pixel (required to be <= 90 meters per pixel for HABSat-1, `L1-SCI-009`, `L2-MIS-074`, `L4-OBC-237`). |
| **HAB (Harmful Algal Bloom)** | Rapid proliferation of toxic cyanobacteria in aquatic ecosystems (such as Lake Erie) targeted by HABSat-1's remote sensing payload (`L0-PRJ-001`). |
| **I2C (Inter-Integrated Circuit)** | A two-wire synchronous serial bus used internally by the ADCS and board-level sensors (`L4-OBC-259`) for short-distance peripheral communication. |
| **Imager Adapter** | The payload interface module that orchestrates the Truth Imager and Multispectral Imager over Camera Link and streams raw image blocks to the Data Processor over UART. |
| **ITAR / EAR** | U.S. International Traffic in Arms Regulations and Export Administration Regulations governing export control and research security (`L1-PRJ-021`, `CON-06`). |
| **LEO (Low Earth Orbit)** | An Earth-centered orbit (typically 350–550 km altitude) where HABSat-1 operates (`L0-PRJ-001`). |
| **LVLH (Local Vertical, Local Horizontal)** | An orbital attitude reference frame aligned with the spacecraft's nadir vector and orbital velocity vector, used for camera pointing and georeferencing (`L2-SYS-040`, `L3-OBC-173`). |
| **Main Computer (OBC)** | The primary flight computer on the EnduroSat OBC Type I board that executes the central state machine, command dispatcher, pass sequencer, and health polling loops. |
| **MPPT (Maximum Power Point Tracking)** | The solar charge controller algorithm on the Power Subsystem that dynamically adjusts electrical load impedance to maximize solar energy harvest. |
| **MRAM (Magnetoresistive Random-Access Memory)** | Radiation-tolerant non-volatile memory connected via SPI used to store critical boot flags, inhibit timers, and parameter tables (`L3-OBC-145`, `L4-OBC-212`, `L4-OBC-264`). |
| **Multispectral Imager** | The primary optical payload camera capturing narrowband imagery at 620 nm, 650 nm, 680 nm, and 708 nm to detect harmful algal blooms (`L1-SCI-008`). |
| **NVM (Non-Volatile Memory)** | Persistent storage media (MRAM, NOR Boot Flash, NAND Flash) that retain data across power cycles and processor resets. |

| **PC/104** | The standardized CubeSat stackable circuit board form factor housing the OBC within its 95 mm x 95 mm x 25 mm volume (`L3-OBC-165`). |
| **PDR (Preliminary Design Review)** | Formal technical milestone review conducted with aerospace industry professionals (`CON-03`). |
| **PPS (Pulse Per Second)** | A hardware timing pulse output by the GPS receiver to synchronize the onboard spacecraft epoch clock (`L4-OBC-218`). |
| **Satellite Operator** | The primary stakeholder role representing authorized UC CubeCats ground personnel who transmit encrypted telecommands and manage orbital passes (`US-01`). |
| **SEU / SEL (Single-Event Upset / Latch-up)** | Radiation-induced transient bit flips (SEU) or parasitic high-current states (SEL) mitigated by shielding, watchdogs, and golden-image boot recovery (`L2-SYS-059`, `L4-OBC-251`). |
| **SoC (State of Charge)** | The remaining usable electrical energy in the spacecraft battery expressed as a percentage of full capacity (`L4-OBC-203`, `L4-OBC-237`). |
| **SPI (Serial Peripheral Interface)** | A 4-wire synchronous serial bus (SCLK, MOSI, MISO, SS) used for high-speed communication between the Main Computer, Data Processor, Data Storage, and S-Band radio. |
| **TLE (Two-Line Element Set)** | A standardized orbital ephemeris format uplinked from the Ground Station (`0x12`) and forwarded to the ADCS (`L3-OBC-151`, `L4-OBC-234`) to compute imaging pass schedules. |
| **Truth Imager** | The RGB context camera paired with the Multispectral Imager to capture visual reference images of Lake Erie (`L4-OBC-223`). |

| **VSWR (Voltage Standing Wave Ratio)** | A measure of radio-frequency impedance matching at the antenna feed (`EC-41`). |
| **WDT (Watchdog Timer)** | Hardware and software countdown timers that trigger a processor reboot or Safe Mode transition if not deterministically strobed within their timeout window (`L4-OBC-250`, `L4-OBC-258`). |
## Functional and Non-Functional Requirements
### Requirements Language & MoSCoW Opt-Out Acknowledgment
The HABSat-1 project defines requirements using standard aerospace modal verbs to denote requirement criticality, **formally opting out of the MoSCoW prioritization framework** in favor of our hierarchical requirement formatting:
- **`"... shall ..."` (Mandatory Requirement):** This requirement must be met by the system or project, or the system will be considered to have failed.
- **`"... should ..."` (Recommended Requirement):** It is strongly recommended to comply with this requirement, but the project will not fail if it is not met.
- **Stable ID & Withdrawal Policy:** Every requirement carries a permanent identifier (`No.` and `L#-XXX-###`). IDs are stable and never reused: when draft requirements `No. 177` through `184` (`L3-OBC-177` to `L3-OBC-184`) were withdrawn during the D1/D2 transition to the dedicated Data Processor architecture, their numbers were permanently retired rather than renumbering `L4-OBC-185` through `L4-OBC-268`.

## Criticality Classification & Scope Boundaries (Opt-Out of MoSCoW Summary)
As stated in Section 5.1, **we have opted out of the MoSCoW summary in favor of our modal-verb requirement formatting (`"shall"` vs. `"should"`) across the `L0`–`L4` requirement hierarchy**. To maintain strict scope governance for our release and ensure excluded capabilities cannot creep back in, our Assignment 9 requirements map to the following scope boundaries:
- **Mandatory Requirements (`"... shall ..."`):** All `"shall"` requirements in the baseline (`L3-OBC-129` through `L3-OBC-131`, `L3-OBC-133`, `L3-OBC-135`, `L3-OBC-137`–`150`, `L3-OBC-152`–`162`, `L3-OBC-164`–`165`, `L3-OBC-168`–`174`, `L4-OBC-185`–`258`, `L4-OBC-260`–`264`, `L4-OBC-267`–`268`). Failure to satisfy any `"shall"` requirement constitutes system failure.
- **Recommended Requirements (`"... should ..."`):** All `"should"` requirements in the baseline (`L3-OBC-132`, `L3-OBC-134`, `L3-OBC-136`, `L3-OBC-151`, `L3-OBC-163`, `L3-OBC-166`, `L3-OBC-167`, `L3-OBC-175`, `L3-OBC-176`, `L4-OBC-259`, `L4-OBC-265`, `L4-OBC-266`). These are strongly recommended and designed into the architecture, though the project will not fail if deferred.
- **Explicit Out-of-Scope / Excluded Features ("Won't" List for This Release — Recorded to Prevent Scope Creep):**
  1. **No Real-Time SGP4 Orbit Propagation on the Main Computer:** Orbital propagation is computationally expensive and runs exclusively on the ADCS Computer (`CMD_ADCS_REQ_SCHEDULE` / `MSG_ADCS_SCHEDULE_PACKET`) and Ground Station; it will not run on the Main Computer.
  2. **No Relational (SQL) Database on the Embedded Flight Computer:** Relational databases introduce dynamic memory overhead and non-deterministic latency that violate hard real-time loop deadlines; onboard storage uses a simpler register/file store in SPI MRAM and NAND Flash (SQLite is restricted strictly to the Ground Station PC).
  3. **No Direct ADCS-to-Imager Triggering Bypassing the Main Computer:** Direct triggering would bypass the centralized SoC (`>= 20%`), GSD (`<= 90 m`), and fault checks (`L4-OBC-237`) managed by the Main Computer.
  4. **No Dynamic Heap Memory Allocation (`malloc`, `new`) During Flight Operations:** Strictly prohibited by `L4-OBC-248` to prevent heap fragmentation and out-of-memory kernel panics.
  5. **No Proprietary Flight OS or Closed Toolchains:** Commercial platforms such as VxWorks are ruled out by `CON-01` and `CON-02`.
